# Architecture

This document describes how Orthobox is built, and why. To add a game, see
[`src/games/README.md`](src/games/README.md), which details the contract to
honour.

Code, comments and documentation are in English; the interface and the game
material are in French, as the application targets French-speaking speech
therapists.

## Overview

Orthobox is a React application served as a static site. There is no server,
no database and no user account: everything runs in the practitioner's
browser, and nothing leaves it.

```
                 ┌──────────────────────────────────────┐
   Gallery  ───► │  Game page: settings, then the game  │
                 └──────────────────────────────────────┘
                                  ▲
                                  │ same game component,
                                  │ same settings
                 ┌────────────────┴─────────────────────┐
   Session  ───► │  Run: game 1, game 2, ..., summary   │
                 └──────────────────────────────────────┘
```

A game does not know whether it was started from the gallery or from a
session. It receives the same props either way and reports the same way, which
avoids maintaining two code paths.

## Layout

```
src/
  assets/fonts/    embedded fonts (Nunito, Atkinson Hyperlegible)
  components/      shared frame, reusable by every game
  games/           one folder per game, plus the registry
  hooks/           reusable state logic
  lib/             data and functions without an interface
  pages/           one page per route
  styles/          global sheets, gallery, game page
public/
  icons/           PWA icons (generated by scripts/generate-icons.mjs)
  sounds/          location of the optional audio files
scripts/           icon generation, preview build
```

## The game registry

`src/games/registry.js` is the only place that knows the list of games, and it
does not hold it: it discovers it at build time.

```js
const modules = import.meta.glob('./*/game.js', { eager: true })
```

Every game folder exposes a `game.js` manifest describing the game (title,
domain, cover, objectives, settings) and pointing at its component as a lazy
import. The registry validates those manifests at startup: a missing required
field, an unknown category or an identifier that does not match the folder
stops the application with an explicit message, rather than producing a
silently incomplete gallery.

Consequence: **adding a game requires modifying no existing file.** That is
the property every evolution must preserve.

## The contract of a game

A game component receives exactly two props:

| Prop | Role |
| --- | --- |
| `config` | settings values, built from `settings` |
| `session` | score counter shared with the frame |

`session.register(true \| false)` is called on every answer. It is the only
channel through which a score travels: neither the game page nor session mode
expects an end screen, since most games can be interrupted halfway through by
the practitioner.

The component is remounted (through a `key`) on every « Démarrer » and every
« Recommencer ». A game can therefore compute its initial state directly in
`useState`, with no reset logic to write.

## Settings

A game describes its parameters declaratively:

```js
settings: [
  { id: 'criterion', type: 'choice', label: '…', default: '…', options: [...] },
  { id: 'rounds', type: 'number', label: '…', min: 5, max: 20, default: 10 },
]
```

`GameSetup` turns that description into controls (`SwitchGroup` for a choice,
`Stepper` for a number) and produces the `config` object. No game draws its own
settings screen: that is what guarantees that all of them are configured the
same way, and that session mode can configure any game without knowing
anything about it.

Values stay raw (`14`, not `'1,4 s'`); only the display is formatted, through
the `unit` field. A config is therefore serialisable as is inside a saved
session.

## Session mode

A session is a list of steps `{ id, gameId, config }`, kept in the browser
(`localStorage`).

- `SessionBuilderPage` composes it: the sequence on the left, the catalogue on
  the right, reorderable by dragging or with the arrows, each step having its
  own settings button.
- `SessionRunPage` runs it: one step at a time, each mounted with its own
  `session`. Moving to the next game is triggered by the practitioner, never by
  the game, and the score at that moment is kept for the final summary.

Drag and drop is hand-written (`hooks/useDragSequence.js`), on Pointer Events:
native HTML5 drag and drop does not work by finger, which would make it
unusable on a tablet. The ongoing gesture is tracked in refs rather than in
React state, because a fast drag can produce both a move and a release within
the same frame, before any new render.

## Adult mode and child mode

`ModeProvider` carries the current mode, keeps it in the browser and sets it on
the root element (`data-mode`). Child mode adds a layer of encouragement,
never a variant of the exercise: neither the settings, nor the material, nor
the score computation depend on the mode.

The companion knows no game. It watches the session, which records the last
answer and increments an event counter on every `session.register()` call; that
counter allows replaying the animation even on two correct answers in a row,
where the state does not change. A new game therefore gets the mascot without
a single extra line of code.

Animations are CSS-based and disappear under `prefers-reduced-motion`, like the
rest of the application.

## Data and privacy

Only three things are written to the browser: the list of favourite games, the
session being prepared, and the display mode. No patient data, no score
history, no network call while in use. `lib/storage.js` guards every access:
private browsing or blocked storage must never keep a game from working.

## Offline

`vite-plugin-pwa` (Workbox) precaches the application on first load. For
offline use to be real, **no remote resource is used**: fonts are embedded in
the repository, illustrations are hand-written SVG, sound effects are
synthesised with Web Audio. Any dependency on a CDN would break that property.

`ORTHOBOX_NO_PWA=1` produces a build without a service worker, used for the
hosted preview.

## Sound

`lib/audio.js` exposes a sound bank whose origin is transparent to the games:

1. if `public/sounds/<id>.mp3` exists, that file is used;
2. otherwise a sound effect is synthesised (oscillators, filtered noise, a
   short convolution reverb).

The repository therefore embeds no audio file, while still allowing one to be
added without touching the code. Animal names, for want of a believable
synthesis, go through the system speech synthesis as long as no file replaces
them.

## Visual identity

Colours live in `lib/categories.js` (three tints per domain) and in the
variables of `styles/global.css`. A component never hard-codes a colour: it
sets `categoryStyle(category)` on a container and uses `var(--category)`,
`var(--category-pastel)` and `var(--category-tint)`. Changing the palette of a
domain therefore only takes editing one object.

Two type families, with distinct roles: Nunito for the interface, Atkinson
Hyperlegible for everything the patient has to read, because it tells `b/d/p/q`
and `I/l/1` apart.

## Interface constraints

They hold for any addition:

- accented French everywhere, game material included;
- no emoji: SVG icons, drawn covers, pictograms;
- touch targets of at least 44 px, and no information carried by colour alone;
- no horizontal overflow, from phone to tablet in landscape.

## Tooling

| Command | Effect |
| --- | --- |
| `npm run dev` | development server |
| `npm run build` | PWA icons, then production build |
| `npm run build:preview` | build without a service worker, ready to publish |
| `npm run lint` | ESLint over the whole repository |
| `npm test` | unit tests (Vitest) |

### What the tests cover

Tests bear on the logic and on the data, where a regression would go
unnoticed: the contract of the game manifests (required fields, usable
settings, defaults within bounds and reachable at the declared step), random
draws, placement without overlap, the order of the steps of a session, the
lenient word comparison and local storage, including when the browser refuses
it.

Rendering, on the other hand, is checked in a real browser, at the three
reference formats: that is where overflows and too-small targets show up,
which unit tests would not catch.

### Continuous integration

`.github/workflows/ci.yml` replays lint, tests and build on `main`, on `integ`
and on every pull request. `.github/workflows/release-please.yml` computes the
version from the commit messages, keeps `CHANGELOG.md` up to date, and creates
the tag and the release when the release pull request is merged.
